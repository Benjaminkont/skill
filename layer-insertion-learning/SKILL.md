# 层插学习法

确定本轮学习对象 a 后，先给一个直接定义，再借周围知识照清它的含义、作用与边界；"是什么"与"属于什么"一起变清楚。

## 使用前提

**学习者已经遇到了某个具体的概念、技术或现象**（a），想要理解它。层插学习法从这个具体起点出发，探索其周围的知识空间。

**适用**：理解具体的事物（"Docker 是什么"、"什么是 JWT"、"Kubernetes 的 Pod 做什么"）  
**不适用**：宽泛的学习目标（"学习后端开发"、"从零开始学 AI"）——这类场景缺少明确的起点，需要先确定具体的学习对象。

起点由学习者的实际需求驱动，不是方法预设的。

## 构建知识树结构

在开始探索前，**必须先确定起点所在的知识树结构**。它是定位起点、锁定同层兄弟、规划探索方向的依据：先在心里把树确定下来，再把需要留档的部分落盘（见下文"产物写到哪里"）。

**知识树的作用**：
- 明确学习对象在哪个"房间"（容器）
- 识别同层的兄弟节点（共同父节点）
- 看清向上和向下的路径

### 读取自带案例库：用 skill 目录的绝对路径

本 skill 自带案例库 `examples/`，随 skill 一起安装。**它在本 skill 的目录下，不在用户的工作目录下**——例如安装在 `~/.codex/skills/layer-insertion-learning/` 时，案例库是 `~/.codex/skills/layer-insertion-learning/examples/`。

查找、读取 `[系统名]-structure.md` 时，一律基于 **SKILL.md 自身所在目录**解析路径，不要用相对当前工作目录的 `examples/`：后者在用户项目里通常不存在，或指向另一个项目的同名目录。同理，本 skill 文档中出现的 `examples/xxx.md`、`references/xxx.md` 都是相对 skill 目录的写法。

### 判断是否可以复用已有 structure

**步骤 1：检查是否有可复用的 structure**

在本 skill 的 `examples/` 目录下查找是否已存在 `[系统名]-structure.md` 文件：
- 如果起点属于该系统（如 `git stash` 属于 Git 系统），复用已有 structure
- 如果不属于任何已有系统，在本轮的工作目录下创建新的 structure（见"步骤 2"）

**可复用的判断标准**：
- ✅ **同一个大系统内**：Git 的所有命令、Python 标准库、React API、Kubernetes 资源
- ✅ **系统边界清晰**：有明确的范围和组成部分
- ✅ **结构相对稳定**：不会频繁大改的知识体系

**不可复用的情况**：
- ❌ **跨系统**：讲 Git 和讲 Docker 不能用同一个 structure
- ❌ **特定项目**：某个具体项目的架构（每个项目不同）
- ❌ **临时性主题**：一次性的、非体系化的知识点

**命名规范**：
- `git-structure.md`、`python-structure.md`：系统级，可复用
- `myproject-structure.md`：项目级或特定主题，不复用

**步骤 2：复用或创建**

**如果复用**：
1. 从 skill 目录 `Read examples/[系统名]-structure.md` 读取完整树
2. 定位起点在树中的位置
3. 裁取父节点 + 同层兄弟节点（1-2 层）
4. 在讲解内容的"知识树定位"章节中显示裁取部分 + ★ 标记
5. 添加引用：`> 完整树参见 [系统名]-structure.md`

**如果创建新 structure**：
1. 在**本轮的工作目录**下创建 `layer-insertion-docs/[系统名]-structure.md`（默认先写这里；用户指定了别处就写别处；见下文"产物写到哪里"）
2. 包含完整的树结构（**推荐 4-5 层深度**）
3. 广度控制在每层 3-5 个节点
4. 在讲解内容中裁取相关部分使用

### 产物写到哪里

**产物写到工作目录，不写 skill 目录。** 触发本方法时，讲解文档与新建的知识树默认写到当前工作目录下的 `layer-insertion-docs/`；用户指定了别处就写别处。单句定义、即时排错、仅需操作步骤这类问题不触发本方法，自然也不产出文件（见 frontmatter 的 description）。

产物与案例库是两回事：

| 内容 | 写到哪里 |
|------|----------|
| 本轮讲解文档（`[主题].md`） | 工作目录下 `layer-insertion-docs/`（用户指定了别处就写别处） |
| 本轮新建的知识树 | 同上，`layer-insertion-docs/[系统名]-structure.md` |
| 修改本 skill 自带的案例库 | 只在用户明确要"扩充案例库"时，且**先确认**再写入 skill 目录的 `examples/` |

**不要**把产物写进 skill 安装目录，除非用户明确要求扩充案例库。skill 目录是共享的方法与案例来源，用户的每次讲解都往里写会污染它。

**深度设计原则**：
- ❌ **太浅（2-3 层）**：看不出"同层"关系，探索空间不足
- ✅ **刚好（4-5 层）**：能清楚识别同层兄弟，结构清晰
- ⚠️ **太深（6+ 层）**：读者容易迷失，维护困难

**示例对比**：

**❌ 太简单（2 层）**：
```
Docker
├── 容器
└── 镜像
```

**✅ 刚好（4 层）**：
```
Docker
├── 镜像层
│   ├── Dockerfile
│   ├── Image
│   └── Registry
└── 运行时层
    ├── Container ★
    ├── Volume
    └── Network
```

### 更改已有 structure 的原则

**可以更改的情况**：
- ✅ **补充缺失节点**：发现某个重要概念未包含在树中
- ✅ **修正明显错误**：层级关系有误、分类不当

**需要谨慎的情况**：
- ⚠️ **大规模重构**：改变整个树的组织方式 → 询问用户是否同意
- ❌ **个别视角调整**：为某个讲解需要不同视角 → 在讲解文档中单独调整，不改 structure

**更改流程**：
1. 发现问题（如缺少 `git restore`）
2. 说明问题："`git-structure.md` 中缺少 git restore，我可以补充进去吗？"
3. 获得确认后更新 structure 文件
4. 继续生成讲解文档

**原则**：structure 文件是"标准视角"，保持稳定；讲解文档可以用"特定视角"，灵活调整。

### 示例：复用 Git structure

`examples/git-structure.md` 是仓库级的 Git 知识树；`git-stash.md`、`git-commit-history.md`、`git-branch-merge.md` 各自裁取其中一段使用。要看完整写法，直接读这三个文件——**裁取的是子树的父子节点，而不是把整棵树抄进每个讲解文档**。

**优势**：
- 单一真相源：只需维护一个 `git-structure.md`
- 阅读体验好：讲解内容自包含，读者一眼看到位置
- 易于扩展：新增 Git 命令时，补充到 structure 即可复用

### 同层判断的三条硬标准

无论复用还是新建知识树，这三条都必须成立：

- **同层 = 同房间**：只有共同父节点的兄弟才是真正的"同层"
- **深度相同 ≠ 同层**：系统中深度相同但在不同分支的节点，不算同层
- **层有作用域**：层不是无限的平面，而是有边界的空间

**类比**：命令行结构
```
mytool
├── init          ← 同层
├── trans         ← 同层
│   ├── english   ← trans 的子层
│   └── japanese  ← trans 的子层
└── ask           ← 同层
```
- `trans` 的同层是 `init` 和 `ask`（不是 `english` 或 `japanese`）
- `english` 的同层是 `japanese`（不是 `init` 或 `ask`）

## 确定学习对象

1. **锁定本轮目标**：结合用户的问题与上下文，明确 a 是概念本身、某个具体事物，还是其中一项机制，以及本轮想弄清什么。能判断就直接开始；仅在歧义会改变讲解路线时澄清。
2. **以对象判断关系**：同层取决于 a 和当前比较视角。学"进程"这一概念时，浏览器进程、播放器进程是实例，可以举例，但不能替代概念的同层对照；学"某个浏览器进程"时，其他具体进程才可能成为同层。不要预设固定的同层配对。
3. **再选择展开方向**：确定对象后，按默认优先级寻找有帮助的关系；没有合适的同层对象，就向上抽或做跨系统对照，不为完成动作硬凑邻居。

## 判断"同层"的标准

**核心原则**：同层 = 同一父节点下的兄弟节点（在同一个"房间"）。

在构建知识树后，同层判断变得明确：
- ✅ Collection 下的 Points、Configuration、Indexes、Payload Schema 是同层
- ❌ Cluster 下的 Node 和 Collection 下的 Points 虽然深度相同，但不在同一房间，不是同层

**辅助判断维度**（当树结构不够清晰时）：
- **功能角色可替换性**：Redis 与 Memcached 都是缓存系统
- **抽象程度相当**：进程、线程、协程都是执行单元
- **共同的上层管理者**：都被操作系统调度
- **互斥的选择空间**：TCP 与 UDP，需要二选一

引入同层邻居时，说明它们的共同点（为什么在同一层）和差异（各自的分工）。选择**最小对比集**（2-3 个典型邻居），覆盖主要差异维度即可，避免"邻居爆炸"。

## 默认优先级

**同层展开 → 向上抽 → 跨系统弱对照 → 向下插。**

1. **同层展开**：引入同房间的兄弟节点，通过共同点、差异或分工理解 a。
2. **向上抽**：沿着知识树向上，看谁在使用或管理它。
3. **跨系统弱对照**：借另一个系统中的 x 展开相关空间 X，反过来理解 a。只取有帮助的联系，交代不能照搬的地方。
4. **向下插**：沿着知识树向下，进入内部结构，看它由什么组成、如何实现。

这是选择路线的默认顺序；没有合适内容或用户指定方向时可以跳过，不强凑四个动作，也不把这份动作表当讲解提纲逐项宣读。

### 向上抽：具体化为使用层

"向上抽"不是抽象的"看上层"，而是具体回答"谁在使用它"。常见的使用层包括：

**容器层**：
- 学习对象所在的容器（Collection 包含 Points，Table 包含 Rows）
- 容器定义了学习对象的存在规则和环境

**操作层**：
- 谁在读取、修改、管理学习对象
- 例如：Query Engine 读取 Rows，API Operations 操作 Points

**理论层**（待扩展）：
- 如果起点既是技术又是理论，可能还需要探索支撑它的理论基础
- 例如：某个算法的数学原理、某个设计模式的理论来源
- **问题**：理论层的边界和探索方式需要进一步明确

向上抽的目标：理解"为什么要这样设计"和"它在更大系统中的角色"。

### 向下插：具体化为内部结构

"向下插"不是随意展开细节，而是沿着知识树向下，看学习对象的内部组成。

**常见的向下路径**：
- **组成部分**：Point 由 Vector、ID、Payload 组成
- **存储结构**：Row 在磁盘上是 B-Tree Cell + ROWID + Record Format
- **实现机制**：异步的 Event Loop、Task Queue、Non-blocking I/O

**何时向下插**：
- 理解了"是什么"和"为什么"后，想知道"怎么做到的"
- 需要理解性能特征、限制条件、底层原理

向下插的目标：理解"它如何工作"和"设计限制的来源"。

### 跨系统对照的风险控制

跨系统对照容易误导，需要明确约束：

- **明确借用范围**：只借用 X 系统的某一个特征，不是全面类比（"进程像工厂车间，都需要分配资源"，仅此而已）
- **主动指出不适用**：说明 X 的其他特征不能套用（"但工厂有实体围墙，进程的隔离是内存地址空间，不一样"）
- **何时不要类比**：目标系统本身已经足够清晰，或找不到合适的对应关系时，直接说明机制，不硬找类比

## 策略

### 转换策略

切换视角前，用贴合当前认识的**反问句**引出相似性、缺口或必要性，让人产生发现或疑问；不要淡然宣布"接下来看看另一个系统"。反问后立即衔接解释，说明新部分与当前目标的联系，不等用户先答题。同一视角内连续讲解无需句句反问。

例如："电视也能联网播放视频，难道它就不需要负责收发网络数据的部件吗？"接着介绍电视的网络部件，再回到网卡，说明这种功能可以存在于不同设备中。

**其他转换方式**（根据内容选择）：

- **对比表格**：多个同层对象的特征需要并列对比时
- **时间线/流程图**：向下插入机制，展示执行顺序时
- **层次关系图**：向上抽时，说明谁管理谁、谁调用谁
- **因果链**：说明"为什么需要它"时，展示前因后果

不是每次都用，而是根据内容选择最清晰的呈现方式。

### 返回与注意力

展开后回答出发时的问题，说明新增认识怎样帮助理解本轮目标。新的部分成为焦点时，旧部分退到背景，需要时再返回；周围知识为目标服务，不要求把整层全部学完。

## 递归条件

引入邻居或上层 b 时，可以说明其基本作用及与 a 的关系；把 b 当成新目标、继续展开其周围或层次，才是递归。

**依据用户回应触发递归**：用户追问或表示想深入 b 时再展开；未表达兴趣则暂时搁置，不逐个节点询问。递归进入新目标后，重新确定学习对象并采用同一优先级，并保留返回原问题的路径。

**递归深度控制**：默认只递归一层，除非用户主动追问。明确当前理解目标：
- **浅层理解**（能用即可）：知道它做什么、何时用、与其他选项的主要区别
- **深层理解**（知其所以然）：理解内部机制、设计权衡、适用边界

根据目标决定何时停止递归。

## 理解验证

不默认安排测验，但在关键节点探测理解状况：

- **关键转换点**：切换到新层次或新对象前，让用户"用自己的话说说看刚才的部分"
- **新场景判断**：给一个变体场景，问"这个属于哪种情况"或"这里该用哪个"
- **自然提问**：不是考试，而是诊断——如果发现理解偏差，立即调整

**识别理解信号**：
- 用户能准确复述核心区别
- 能判断新场景的归属
- 主动提出相关问题或联系

**识别误解信号**：
- 混淆同层对象与实例
- 类比过度（把跨系统对照当成完全等同）
- 无法判断简单场景

发现误解时，回到出问题的节点，用不同角度重新展开。

## 与其他学习方法的关系

层插学习法关注**认知导航**（在理解空间中该往哪走），可以与其他方法组合使用：

- **费曼学习法**：层插解决"讲什么"（路径选择），费曼解决"怎么讲"（用简单语言）
- **5W1H 框架**：5W1H 是完整性检查清单，层插是动态导航路径
- **思维导图**：思维导图呈现静态全景，层插提供动态探索路径
- **苏格拉底问答法**：反问句策略借鉴了苏格拉底法，但层插更强调方向选择

层插的定位：在复杂知识空间中，**根据当前理解状态选择下一步方向**，而不是提供固定的讲解模板或知识组织方式。

## 实施注意事项

作为 AI 使用时：

- **内部步骤 vs 对外输出**：知识树、同层判断、方向选择都是**内部**的思考步骤，先把它们想清楚，再落盘成文档；对外呈现的是解释本身，不必汇报"我走了哪几步"。用户询问"你是怎么讲的"时再说明使用了层插法。
- **落盘位置**：产物写到工作目录 `layer-insertion-docs/`，不要写 skill 安装目录（规则见上文"产物写到哪里"）。
- **避免机械套用**：不要在解释中说"现在我们做同层展开、接下来向上抽"，而是自然过渡
- **保持简洁**：不是每个概念都需要完整走完四个方向，根据实际需要选择

**自检清单**（每次解释后）：
- [ ] 是否明确了学习对象的类型（概念/实例/机制）？
- [ ] 引入的邻居是否真的"同层"？
- [ ] 跨系统对照是否指出了不适用的地方？
- [ ] 是否在关键点验证了理解？
- [ ] 解释是否服务于用户的实际问题，而不是为了展示方法？
- [ ] 产物是否写在工作目录 `layer-insertion-docs/`，而非 skill 安装目录？

结合用户反馈判断理解缺口并调整讲解，不默认安排测验。
