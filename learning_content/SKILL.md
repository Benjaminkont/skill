# 学习代码的注释方法

让读者先看清代码结构，再理解关键步骤、设计边界和运行过程。默认只处理用户指定的文件与学习主题；整理已有注释时保留代码行为、原有说明及示例。用户要求“内容不变”时，只调整注释标记、位置和排版；发现说明与实现不符时指出差异，不夹带逻辑修改或擅自修正说明。

## 按结构分层

- **文件顶部 docstring**：简要说明本文件的学习目标与来源。有可核实来源时记录，不编造出处。
- **分隔线标题**：划分类、数据结构或功能组。沿用目标文件的标题宽度与缩进，不为每个小步骤添加分隔线。
- **函数或方法 docstring**：说明整体作用、输入输出中容易误解的语义及必要的行为边界。简单函数可以只写一句，复杂函数可加入过程示例；按需提供 Args、Returns、Raises，不强行填满模板。
- **局部注释**：放在对应字段、语句或代码块旁，解释读者在这里需要理解的内容。

## 按说明用途分类

| 写法 | 用途 | 内容选择 |
| --- | --- | --- |
| `#*   ...` | 字段含义、重点概念、关键步骤 | 说明状态保存什么、步骤如何推进；复杂流程可编号 |
| `#!   ...` | 约束、设计原则、异常边界 | 哪些条件必须成立、为什么需要保留边界、何时无法继续 |
| `#?   ...` | 语法解释、变量含义、具体推演 | 解释不熟悉的写法，用例子展示数据与状态变化 |
| `#TODO   ...` | 真实存在的待办 | 只标记尚未完成的事项，不为了展示标记制造任务 |
| `#//   ...` | 已废弃或停用的代码 | 仅在确有此含义时使用，不用于正常教学示例 |

普通补充说明可以使用普通注释。不要把每行代码都机械地翻译成中文，也不要对每个注释强行套用某个标记。

## 用例子解释机制

在抽象逻辑难以直接看懂时，选择最有帮助的一种形式：

- 用节点序列、树形图展示父子关系、遍历顺序或分支变化。
- 用具体的输入、列表、切点和输出展示状态如何变化。
- 将推导式等紧凑表达式展开为等价循环，明确标为解释性示例，保留原实现。
- 给较复杂流程标出主要阶段，让读者能顺着代码追踪执行过程。

例子应符合当前实现。尤其检查方向、保留范围、计数与预算单位，避免把算法未保证的行为写成承诺。新增例子可以采用简化数值，但应标明假设。无需每个函数同时配齐以上形式。

## 精确排版约定

这些是本技能采用的用户约定，不作为通用 Python 标准推广。

1. **`#` 与语义标记零空格**：使用 `#!`、`#?`、`#*`、`#TODO`、`#//`。
2. **标记后留三个基础空格**。示例代码与树形图自身的缩进额外保留；同一组注释的标记仍纵向对齐。
3. **代码与行尾注释之间至少五个空格**。连续的同组字段，其 `#` 放在同一列。
4. **跨行括号组中的行尾注释整体右移**：对于 `()`、`[]`、`{}`，忽略注释后，找到该组包含起止行在内的最长代码行；该组的行尾 `#` 对齐到最长行右侧至少两个空格，同时满足每行代码与 `#` 至少间隔五个空格。默认放在最长代码行之后五个空格的位置。独占一行的解释性注释保持正常代码缩进，不因处于括号内而移到右侧。
5. 保持示例的相对缩进和图形结构。使用空格，不用 Tab 凑对齐；改完后检查实际文件，不只描述预期格式。

字段注释示例：

```python
name: str            #*   Skill 的名称
description: str     #*   Skill 的功能描述
path: str            #*   Skill 正文文件的位置
```

括号组与函数说明示例：

```python
# ------------------------------ 项目指令组装 ------------------------------ #
def join_instructions(
    instructions: list[str],
    separator: str = "\n\n",     #?   相邻项目指令之间的分隔符。
) -> str:
    """用指定分隔符连接项目指令。"""
    #!   保持调用者提供的原始顺序。
    #?   join 在相邻元素之间插入分隔符。
    return separator.join(instructions)
```

解释性代码示例：

```python
#?   skill = Skill(
#?       name="python",
#?       description="Python 编程技能",
#?       path=Path("skills/python.md")
#?   )
```

后三行参数前的额外空格属于示例自身的缩进，`#?` 内部始终没有空格。

## 修改与核对

先阅读实际文件和局部约定，判断已有注释各自承担的作用，再按需调整。Better Comments 提供标记着色，Comment Divider 帮助生成标题，autoDocstring 帮助生成函数文档模板；不依赖插件完成注释，也不自动安装插件或修改编辑器设置。

交付前回读文件，检查标记紧贴、基础间距、同组对齐、括号组最长行以及示例缩进。对于仅调整 Python 注释的修改，检查语法并比较修改前后的 AST；如果新增或移动 docstring，应单独核对文档变化，并确认可执行语句保持一致。不要为排版改动调用真实模型或外部业务服务。

最终简要说明修改的文件、采用的规则和实际执行的检查。只要求总结时直接总结，不自行修改文件。
