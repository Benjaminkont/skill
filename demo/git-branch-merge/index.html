🌳 Git 分支合并可视化

Git Merge - 保留完整历史

Merge 创建一个新的"合并提交"，它有两个父提交。就像两条河流汇合，能看到各自的来源。

main 分支
feature 分支
merge 提交
步骤 1
合并前
步骤 2
git merge feature
$ git checkout main # 切换到 main 分支 $ git merge feature # 把 feature 合并进来，创建合并提交 M # M 有两个父提交：main 的 B 和 feature 的 Y
特点 说明
✓ 保留历史 完整保留两个分支的开发历史，知道代码从哪来
✓ 安全 不改变任何已有提交，只追加新提交
✗ 历史复杂 多分支频繁合并时会产生"意大利面条"式的历史
✗ 额外提交 每次合并都会产生一个合并提交

Git Rebase - 线性化历史

Rebase 把你的提交"搬到"目标分支的最新提交之后，形成一条直线。提交会被重写，SHA 改变。

main 分支
feature 分支（旧）
feature 分支（新）
步骤 1
Rebase 前
步骤 2
git rebase main
$ git checkout feature # 切换到 feature 分支 $ git rebase main # 把 feature 的提交（X, Y）"搬到" main 的最新提交（B）之后 # X 和 Y 被重写为 X' 和 Y'（SHA 改变了！）
特点 说明
✓ 历史整洁 形成一条清晰的直线，易于阅读和理解
✓ 无额外提交 没有合并提交，提交历史更简洁
⚠ 改写历史 提交的 SHA 会改变，历史被"重写"
✗ 危险 已推送的公共分支绝对不能 rebase！

⚠️ Rebase 黄金法则

永远不要 rebase 已经推送到公共分支的提交！

  • ✓ 私有分支可以随意 rebase（还没推送的）
  • ✗ main、develop 等公共分支绝对不能 rebase
  • 原因：SHA 改变后，其他人的工作会无法合并

Git Cherry-Pick - 精确挑选

Cherry-Pick 只挑选特定的提交应用到当前分支。就像从菜单上只点你想要的菜，而不是套餐。

main 分支
feature 分支
cherry-pick 的提交
步骤 1
挑选前
步骤 2
git cherry-pick Y
$ git checkout main # 切换到 main 分支 $ git cherry-pick abc123 # 只把提交 Y 的改动复制过来 # 创建新提交 Y'（内容相同，但 SHA 不同）
特点 说明
✓ 精确控制 只挑选需要的提交，不会带来其他改动
✓ 灵活 可以跨分支复制改动，适合紧急修复场景
⚠ 产生副本 是复制提交而不是移动，会产生重复
✗ 易混乱 频繁使用会让历史变得混乱，难以追踪

三者对比 - 同一起点，不同结果

从相同的起点出发，三种合并方式产生三种完全不同的历史结构。

起点：main 和 feature 各自开发了一段时间
方式 1: Merge

保留分叉，创建合并提交

方式 2: Rebase

线性化，提交被"移动"

方式 3: Cherry-Pick（只要 Y）

精确挑选，只复制需要的提交

对比维度 Merge Rebase Cherry-Pick
历史结构 树状（保留分叉） 线性（一条直线） 追加式
是否改变已有提交 ✓ 不改变 ✗ 改变 SHA ✓ 不改变原提交
公共分支安全性 ✓ 安全 ✗ 危险 ✓ 安全
适用场景 功能分支合并到主线 私有分支同步更新 紧急修复、特定改动

💡 选择建议

  • 功能分支合并到 main → 用 merge --no-ff
  • 私有分支同步主线 → 用 rebase
  • 整理未推送的提交 → 用 rebase -i
  • 特定修复应用到多个分支 → 用 cherry-pick
  • 已推送的公共分支 → 绝对不要 rebase！
