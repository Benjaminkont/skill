# 从真实源码到教学 MVP

把“我想参考这些项目的这个模块”转成可追溯、可阅读、可观察的小实验。学习对象可以是任何软件机制，不限于 Agent Harness，也不预设语言、框架或项目名单。

## 先确定学习问题与授权范围

- 从用户给出的项目、目标模块和已有对话中提取：想弄懂什么、要观察什么行为、希望产出分析还是可运行代码。
- 把宽泛模块名收敛到一个能追踪的机制，例如“context”中的“历史如何选择和压缩”，而不是一次复现整个 context 子系统。
- 已明确的约束直接沿用；仅对影响学习主线的缺口提问。用户只要求分析时保持只读；已要求实现时，在其范围内继续完成，不增加逐阶段确认手续。
- 实现前检查真实目标路径、局部约定、已有代码和用户改动，沿用实际技术栈。用户中途移动目录时，重新定位并核对导入、运行说明和调用处。

## 定位并分析真实实现

- 核实项目身份、官方仓库或用户给定的本地来源、源码可访问范围。名称有歧义时先消除歧义；不能用同名项目或第三方分析补成官方源码。
- 优先固定 commit/tag，同时记录实际阅读的文件和相关符号；取不到固定版本时标注查阅日期。不要把能读到的旧快照称为最新 HEAD。
- 从入口沿调用关系追踪状态、输入输出与关键失败路径，读到足以解释机制为止，不把 README 的功能介绍当实现证据。
- 源码事实、基于源码的推断、教学选择分开写。文档和行为观察只能作为相应类别的补充；取不到源码时明确留下证据缺口，不编造实现，也不把猜测包装成该项目的 MVP。
- 多个项目的独立调研可在当前环境允许时委派；要求返回机制、版本、文件/符号、适用条件与未确认事项。主 agent 核对关键证据和结论分歧。

## 选择学习主线

- 为值得保留的实现找一条清晰的数据流或状态变化主线，用一句话说明它解决什么问题。
- 依据用户的问题选择主线，不按代码短、抽象少或“优雅”给整个项目排名；解释差异来自哪些约束和取舍。
- 不强求每个项目各做一个 MVP。相近机制可合并，关键分歧才分别实验；尊重用户明确要求的项目覆盖范围。
- 简短说明将保留的机制、配套能力如何处理、准备观察哪些行为，再落实到代码。不要为了复刻原项目目录而复制整个架构。

## 构造最小实验

- 当前机制保持可见：入口、关键状态、选择/转换过程和输出应能顺着阅读。以一个示例独立可读为优先，接受适量重复。
- 配套能力用最小真实实现、固定接口、stub 或 mock；明确标记其来源与行为差异。不要把当前主题的重要逻辑藏进笼统的 support/utils 中。
- 必须共享代码时说明共享部分承担什么职责；区分上游机制的改写、本地通用辅助、测试假数据与真实服务适配器，不能让自写辅助层冒充上游结构。
- 列出本次机制不能被简化掉的不变量，围绕它们决定切点、状态提交和错误处理。例如历史压缩须维持工具配对，缓存淘汰须维持容量/过期语义；不要把某个例子的不变量推广为所有主题的固定要求。
- 若简化删掉了目标问题的关键难点，就缩小实验结论或增加必要的真实实现。涉及并发、性能、缓存命中、模型效果时，纯同步/mock 实验通常不能支持产品级结论。
- 提供最少运行步骤、可观察的输入/状态变化/输出，以及一个围绕当前机制的小修改练习。不要引入无关依赖、通用框架或生产基础设施。
- 复制上游实质代码或模板时保留必要的来源及许可证；独立重写时如实描述参考关系。

## 验证理解并回到源码核对

- 根据目标机制验证正常路径和有意义的失败边界；测试不必照着每个实现分支逐项复制。
- 选择可以推翻错误理解的观察：例如切换分支后不串历史、状态提交失败不污染旧状态、容量或过期边界保持一致。
- 对照上游重新检查每个关键机制，尤其是省略后的行为差异。独立审查有价值且允许委派时，可交给另一 agent，但结论仍需核实。
- 明确区分静态检查、离线 mock、真实依赖和真实服务运行。只报告实际执行过的检查；估算值、成功序列化或 mock 通过不能替代真实效果验证。
- 新发现与当前机制直接相关的问题应修正或明确留下，不能用“测试通过”覆盖未测试的入口与能力。

## 交付时保留证据对应关系

按本次范围提供简短说明；用户要代码时，把必要来源与运行说明放在学习目录中，代码聚焦实现。不要为简单任务强制生成一整套计划、报告或固定目录。

用下表或等价的清晰叙述交代学习结果；行数由实际机制决定：

| 机制 | 上游怎么做（版本、文件、符号） | MVP 保留什么（本地入口） | 简化掉什么及行为差异 | 验证到了什么、尚未验证什么 |
|---|---|---|---|---|

“保留了同样的机制”必须有代码对应；“验证到了”必须有执行证据。最后说明实验能支持的结论范围，避免把教学 MVP 的可读性或 mock 运行结果推广到原项目整体优劣。
